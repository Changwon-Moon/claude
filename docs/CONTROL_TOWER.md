# 관제탑(Control Tower) — 에이전트 판단의 시각적 관리·감독 설계

> 2026-07-19 운영자 방향: 콘텐츠 제작 전 과정을 코드 대화창이 아닌 **시각적 인터페이스**로 관리·감독·수정보완한다. 각 AI 팀(리서치·기획·편집·품질검수·디자인·마케팅)의 **판단과 근거**를 눈으로 보고 통제하는 것이 목표. (M9 대시보드의 상위 개념 — 본 문서가 M9의 설계 원천)

## 1. 제1원칙: UI보다 데이터 구조가 먼저

**모든 에이전트 출력은 "판단(claim) + 근거(evidence) + 출처(source) + 확신도(confidence)"를 가진 구조화된 JSON으로 남긴다.** 대시보드는 그 기록의 뷰(view)일 뿐이다.

- 이미 파이프라인은 파일(JSON) 계약으로 설계됨(ARCHITECTURE.md §2) → UI는 언제든 갈아끼울 수 있는 표피
- 에이전트를 새로 만들 때마다 이 "판단 기록 스키마"를 의무화하면, 관제탑에 자동으로 나타난다

### 판단 기록 공통 스키마 (초안)

```jsonc
{
  "agent": "planner",              // researcher | planner | editor | factcheck | design-qa | caption
  "ticketId": "2026-07-19-001",    // 콘텐츠 1건 = 티켓 1장
  "at": "2026-07-19T07:12:00Z",
  "decision": "ranking-table로 제작 추천",   // 판단(사람이 읽는 한 줄)
  "reasons": [                      // 근거 목록
    { "text": "커뮤니티 화제성 높음", "source": "https://...", "score": 3 }
  ],
  "rubric": { "시의성": 3, "데이터": 2, "저장가치": 3, "관심폭": 3, "우리다움": 2 },
  "confidence": 0.8,
  "needsHuman": false,              // 사람 개입 요청 플래그
  "artifacts": ["data/plans/2026-07-19/plan-001.json"]  // 산출물 링크
}
```

## 2. 화면 구성

### 메인: 파이프라인 칸반
`소재후보 → 기획안 → 제작중 → 검수대기 → 승인대기 → 예약/발행 → 성과측정`
- 콘텐츠 1건 = 티켓 1장. 티켓에 썸네일(렌더 미리보기)·Tier·포맷·담당 단계 표시
- 오케스트레이터(M8) 상태 머신의 상태와 1:1 대응

### 티켓 상세: 팀별 판단 타임라인
각 팀 에이전트의 판단이 시간순으로 쌓인다. 팀별 특화 뷰:

| 팀 | 보여줄 것 |
|---|---|
| 🔎 리서치 | 소재 신호(제목·링크), rubric 점수, 왜 지금인지 |
| 📋 기획 | 선정 이유, Tier·포맷 결정, 제목 시안들, 발행 슬롯 |
| ✏️ 편집 | **수치 대조표**: 카드에 들어갈 값 ↔ 원본(raw) 값 ↔ provenance 경로 |
| 🧐 품질검수 | 팩트체크 PASS/FAIL + 사유, 디자인 QA 결과(문제 위치 하이라이트) |
| 🎨 디자인 | 렌더된 카드 이미지(버전 비교 슬라이더) |
| 📣 마케팅 | 캡션·해시태그 후보, 발행 시간 제안 |

### 단계별 액션 (사람의 개입 지점)
- `[✅ 승인]` `[✏️ 수정지시]` `[❌ 반려]`
- 수정지시는 **자연어 코멘트** → 해당 에이전트가 코멘트를 입력받아 재작업 → 새 버전이 타임라인에 추가
- 모든 개입도 기록으로 남는다 → 이 기록이 곧 에이전트 학습 데이터(RESEARCH_WORKFLOW §4와 동일 철학)

### 성과 탭
- [소재 카테고리 × 포맷] 히트맵(도달·저장률), 최근 발행 성과 목록
- 기획 에이전트의 스코어링 가중치에 피드백되는 데이터와 동일 소스

### v2 개정 (2026-07-19, 조직 개편 반영)
- **티켓 점수 이중 표기**: 수요 점수(터질 것) × 데이터 점수(만들 수 있는 것) — 6축 rubric([AGENTS.md](./AGENTS.md))
- **탭 추가**: ① 패턴 라이브러리(터진 공식 모음, 트렌드분석팀) ② 자산 허브(로고·사진·데이터셋 현황과 재사용률, 자료허브팀) ③ 성과 보드
- **상단 KPI 4개 상시 표시**: 주간 발행수 · 저장률 · 팔로워 · 콘텐츠 단가 (마케팅·성장팀 KPI와 동일)

## 3. 구현 로드맵 (3단계 진화)

| 단계 | 방식 | 상호작용 | 인프라 | 시기 |
|---|---|---|---|---|
| **A. 파일 기반** (가동 중) | GitHub의 md 보드·로그 (소재보드 체크박스, IDEAS, DECISION_LOG) | GitHub 앱에서 편집 | 0원 | ✅ 지금 |
| **B. 정적 관제탑** (다음) | 파이프라인 산출물(JSON·PNG)을 읽어 **정적 HTML 생성** → GitHub Pages 자동 게시. 세션에서는 아티팩트로 미리보기 | 읽기 중심. 승인 등은 링크 우회(GitHub 편집·이슈) | 0원, 서버 없음 | 1~2세션 |
| **C. 웹 대시보드** (M9) | Next.js + DB + 서버. 버튼이 실제 파이프라인을 구동(승인→발행, 수정지시→에이전트 재실행) | 완전 상호작용, 인라인 편집 | 월 $5~20 | M6~M8 이후 |

**B를 먼저 하는 이유**: 아직 에이전트(M6~M8)가 없어 "움직일 버튼"이 없다. 반면 보여줄 데이터(소재보드·렌더 카드·결정로그)는 이미 있다. 읽기 전용 관제탑을 먼저 세우면 에이전트가 생길 때마다 판단이 자동으로 나타나고, C에서 버튼만 살아난다.

## 4. 기술 선택 메모

- **B 단계**: 정적 HTML 생성기는 렌더러와 같은 스택(HTML/CSS, 빌드 시 JSON 주입). GitHub Actions가 파이프라인 실행 후 관제탑 페이지도 재생성·게시. 모바일 우선 레이아웃.
- **C 단계**: Next.js(웹) + SQLite→Postgres(상태·판단기록) + 오케스트레이터 API. Telegram 봇(M8)과 같은 상태를 바라봄 — 봇은 "빠른 승인", 웹은 "깊은 검토"로 역할 분담.
- 아티팩트(claude.ai 웹페이지 발행)는 **시안·목업·1회성 리뷰**에 활용(빠름). 상시 운영 화면은 Pages/서버로.

## 5. 진행 상황

1. ✅ 목업을 아티팩트로 만들어 방향 확정 (2026-07-19)
2. ✅ **B 단계 구축 완료** — `packages/dashboard-static` 생성기:
   - **상태 빌더**(`buildState.ts`): 저장소 산출물(소재보드·결정로그·회사문서·자산카탈로그·렌더카드)을 읽어 단일 `tower-state.json`으로 집계. 결정적(동일 저장소=동일 JSON).
   - **HTML 생성기**(`renderHtml.ts`): 목업과 동일한 룩에 데이터 주입 → 자체 완결 `index.html`(썸네일 base64 임베드, 오프라인/아티팩트 모두 열림). 탭 3개(파이프라인·회사·자산) + KPI 스트립 + 지시 전달함.
   - **파서 셀프테스트** 23종, **데일리 워크플로**에 재생성·업로드 배선.
   - 실데이터 검증: 후보 9 + 승인대기 2(아파트 카드 실렌더 썸네일 포함) + 원칙 27 + 팀 9 + 자산 6.
3. ✅ **회사 편집 기능** — CEO 원칙 + 9팀 원칙/프롬프트를 관제탑에서 직접 수정보완. 서버 없이 두 경로: (a) 관제탑 편집 → 지시 전달함 → [요약 복사] → Claude가 파일 반영·학습기록, (b) 각 문서(company/*, prompts/*) GitHub 직접 편집 링크. 런타임 프롬프트는 `prompts/{team}.md`(초안 9종)로 실존.
4. 🟡 **GitHub Pages 배포** — `.github/workflows/pages.yml` + [가이드](./guides/control-tower-pages.md). 운영자가 Settings→Pages→Source=GitHub Actions 1회 설정하면 상시 URL. (CI 빌드엔 썸네일 빠질 수 있음 — 원본 gitignore)
5. ✅ **아티팩트 발행** — 세션에서 body-only(`artifact`) 산출 → 비공개 아티팩트. 썸네일 포함 완전판.
6. ⬜ 에이전트(M6~) 구현 시 "판단 기록 스키마"(§1) 의무 적용 → 관제탑 타임라인에 자동 출현
