# 관제탑(Control Tower) — 에이전트 판단의 시각적 관리·감독 설계

> ⚠️ **2026-07-30 표준 축소(오너 승인).** 아래 설계 중 결정함·파이프라인 칸반·지시함·요청 대장·성과 탭은
> **폐지됐다.** 실제 공장·입구는 채팅(작업 세션)이고, 관제탑은 ①발행(결재 대기·올릴 차례·발행 이력)
> ②소재 보드 ③보관함 ④회사 ⑤자산 — **보고, 기록하는 곳**만 맡는다.
> 신규 소재·지시의 단일 입구는 채팅이다. 이 문서의 나머지는 설계 사료로 남긴다(판단 기록 스키마 §1은 유효).

> 2026-07-19 운영자 방향: 콘텐츠 제작 전 과정을 코드 대화창이 아닌 **시각적 인터페이스**로 관리·감독·수정보완한다. 각 AI 팀(리서치·기획·편집·품질검수·디자인·마케팅)의 **판단과 근거**를 눈으로 보고 통제하는 것이 목표. (M9 대시보드의 상위 개념 — 본 문서가 M9의 설계 원천)

## 1. 제1원칙: UI보다 데이터 구조가 먼저

**모든 에이전트 출력은 "판단(claim) + 근거(evidence) + 출처(source) + 확신도(confidence)"를 가진 구조화된 JSON으로 남긴다.** 대시보드는 그 기록의 뷰(view)일 뿐이다.

- 이미 파이프라인은 파일(JSON) 계약으로 설계됨(ARCHITECTURE.md §2) → UI는 언제든 갈아끼울 수 있는 표피
- 에이전트를 새로 만들 때마다 이 "판단 기록 스키마"를 의무화하면, 관제탑에 자동으로 나타난다

### 판단 기록 공통 스키마 (초안)

```jsonc
{
  "agent": "planner",              // researcher | planner | editor | factcheck | design-qa | caption
  "ticketId": "2026-07-19-001",    // 콘텐츠 1건 = 티켓 1장
  "at": "2026-07-19T07:12:00Z",
  "decision": "ranking-table로 제작 추천",   // 판단(사람이 읽는 한 줄)
  "reasons": [                      // 근거 목록
    { "text": "커뮤니티 화제성 높음", "source": "https://...", "score": 3 }
  ],
  "rubric": { "시의성": 3, "데이터": 2, "저장가치": 3, "관심폭": 3, "우리다움": 2 },
  "confidence": 0.8,
  "needsHuman": false,              // 사람 개입 요청 플래그
  "artifacts": ["data/plans/2026-07-19/plan-001.json"]  // 산출물 링크
}
```

## 2. 화면 구성

### 메인: 파이프라인 칸반
`컨텐츠 마이닝 → 기획안 → 제작중 → 검수대기 → 승인대기 → 예약/발행 → 성과측정`
- 콘텐츠 1건 = 티켓 1장. 티켓에 썸네일(렌더 미리보기)·Tier·포맷·담당 단계 표시
- 오케스트레이터(M8) 상태 머신의 상태와 1:1 대응

#### ~~컨텐츠 마이닝 패널 (첫 열 = 화면 1/3 폭)~~ → **폐지 (2026-07-26, §4c)**
> 소재 고르기가 파이프라인 첫 열과 💡소재 탭 두 곳으로 갈라져 서로 따로 놀았다.
> **💡소재 탭 하나로 일원화**하고 칸반은 '기획안'부터 그린다. 아래는 폐지 전 기록.

소재 발굴의 작업대. 정적 관제탑에선 백엔드가 없어 **다리(지시 전달함)** 로 실동작, C단계에서 버튼이 백엔드 직결로 승격된다.
- **주제 비중 설정**: 부동산30·경제일반20·주식15·기타35(기본, 편집 가능, 합 100 검증)
- **[마이닝 실행]**: 비중을 실어 "실시간 수집 요청"을 지시 전달함에 담음 → [요약 복사] → Claude(리서치·트렌드분석)가 웹/RSS/통계를 돌려 후보 10건 생성 → 다음 갱신에 표출
- **후보 목록**(스크롤 누적): 각 후보에 주제·출처·선정 사유 + [선정/탈락/상세]. 선정=기획안 이동, 탈락=제외
- **학습 루프**: 선정/탈락이 학습신호(선호/비선호)로 지시 전달함에 흘러 → 트렌드분석·리서치 팀의 수요 가중치·프롬프트에 반영 (R0 수동 → M6 자동)
- **지식 인풋 채팅창**(하단): 기사·메모 붙여넣기(텍스트 즉시 반영), 이미지 붙여넣기(미리보기·첨부 표시 — 실제 전달은 세션 업로드)

### 티켓 상세: 팀별 판단 타임라인
각 팀 에이전트의 판단이 시간순으로 쌓인다. 팀별 특화 뷰:

| 팀 | 보여줄 것 |
|---|---|
| 🔎 리서치 | 소재 신호(제목·링크), rubric 점수, 왜 지금인지 |
| 📋 기획 | 선정 이유, Tier·포맷 결정, 제목 시안들, 발행 슬롯 |
| ✏️ 편집 | **수치 대조표**: 카드에 들어갈 값 ↔ 원본(raw) 값 ↔ provenance 경로 |
| 🧐 품질검수 | 팩트체크 PASS/FAIL + 사유, 디자인 QA 결과(문제 위치 하이라이트) |
| 🎨 디자인 | 렌더된 카드 이미지(버전 비교 슬라이더) |
| 📣 마케팅 | 캡션·해시태그 후보, 발행 시간 제안 |

### 단계별 액션 (사람의 개입 지점)
- `[✅ 승인]` `[✏️ 수정지시]` `[❌ 반려]`
- 수정지시는 **자연어 코멘트** → 해당 에이전트가 코멘트를 입력받아 재작업 → 새 버전이 타임라인에 추가
- 모든 개입도 기록으로 남는다 → 이 기록이 곧 에이전트 학습 데이터(RESEARCH_WORKFLOW §4와 동일 철학)

### 성과 탭
- [소재 카테고리 × 포맷] 히트맵(도달·저장률), 최근 발행 성과 목록
- 기획 에이전트의 스코어링 가중치에 피드백되는 데이터와 동일 소스

### v2 개정 (2026-07-19, 조직 개편 반영)
- **티켓 점수 이중 표기**: 수요 점수(터질 것) × 데이터 점수(만들 수 있는 것) — 6축 rubric([AGENTS.md](./AGENTS.md))
- **탭 추가**: ① 패턴 라이브러리(터진 공식 모음, 트렌드분석팀) ② 자산 허브(로고·사진·데이터셋 현황과 재사용률, 자료허브팀) ③ 성과 보드

## 3. 구현 로드맵 (3단계 진화)

| 단계 | 방식 | 상호작용 | 인프라 | 시기 |
|---|---|---|---|---|
| **A. 파일 기반** (가동 중) | GitHub의 md 보드·로그 (소재보드 체크박스, IDEAS, DECISION_LOG) | GitHub 앱에서 편집 | 0원 | ✅ 지금 |
| **B. 정적 관제탑** (다음) | 파이프라인 산출물(JSON·PNG)을 읽어 **정적 HTML 생성** → GitHub Pages 자동 게시. 세션에서는 아티팩트로 미리보기 | 읽기 중심. 승인 등은 링크 우회(GitHub 편집·이슈) | 0원, 서버 없음 | 1~2세션 |
| **C. 웹 대시보드** (M9) | Next.js + DB + 서버. 버튼이 실제 파이프라인을 구동(승인→발행, 수정지시→에이전트 재실행) | 완전 상호작용, 인라인 편집 | 월 $5~20 | M6~M8 이후 |

**B를 먼저 하는 이유**: 아직 에이전트(M6~M8)가 없어 "움직일 버튼"이 없다. 반면 보여줄 데이터(소재보드·렌더 카드·결정로그)는 이미 있다. 읽기 전용 관제탑을 먼저 세우면 에이전트가 생길 때마다 판단이 자동으로 나타나고, C에서 버튼만 살아난다.

## 4. 기술 선택 메모

- **B 단계**: 정적 HTML 생성기는 렌더러와 같은 스택(HTML/CSS, 빌드 시 JSON 주입). GitHub Actions가 파이프라인 실행 후 관제탑 페이지도 재생성·게시. 모바일 우선 레이아웃.
- **C 단계**: Next.js(웹) + SQLite→Postgres(상태·판단기록) + 오케스트레이터 API. Telegram 봇(M8)과 같은 상태를 바라봄 — 봇은 "빠른 승인", 웹은 "깊은 검토"로 역할 분담.
- 아티팩트(claude.ai 웹페이지 발행)는 **시안·목업·1회성 리뷰**에 활용(빠름). 상시 운영 화면은 Pages/서버로.

## 4b. C단계 진입 — 직접 실행 관제탑 (2026-07-26)

관제탑이 "보여주고 복사시키는 화면"에서 **"눌러서 저장소를 바꾸는 도구"**가 됐다.

| 무엇 | 어디에 기록되나 |
|---|---|
| 소재 승인·보류·거부·수정·삭제·추가 | `research/ideas.json` (Contents API PUT, 저장 직전 sha 재확인) |
| 소재 발굴 요청 / 티켓 승인·보류·반려·수정지시 / 회사 원칙 편집 | `research/decisions-inbox.md` (append) |
| 자료 인박스 | `research/INBOX.md` (append) |
| 마이닝 실행 | 워크플로 dispatch |

**설계 원칙**
- **단일 원천**: 소재는 `research/ideas.json` 하나. 화면은 그 뷰일 뿐이고, 조작하면 같은 파일을 되쓴다.
- **우회 폐기**: 지시 전달함·요약 복사·초기화 제거. 복사-붙여넣기 경로가 사라졌다.
- **미연결 = 읽기 전용**: 토큰이 없으면 조작해도 **상태를 바꾸지 않는다**. 새로고침에 사라질 변경을 만들지 않기 위함.
- **연타 보호**: 저장은 800ms 디바운스로 묶어 커밋이 쏟아지지 않게 한다.
- **소재 보드 흡수**: 별도 `ideas.html` 폐기 → 관제탑 `💡 소재` 탭. 구 북마크는 `/#ideas`로 리다이렉트.
- **회귀 방지**: `scripts/smoke-tower.mjs` 17항목이 배포 전마다 돈다(읽기 전용 게이트·실제 쓰기 경로 확인).

## 4c. 대규모 개편 — 결정함 중심 + 승인이 실행으로 (2026-07-26)

C단계에서 "눌러서 저장소를 바꾸는 도구"가 됐지만, **오너가 뭘 결정해야 하는지가 화면에 안 보였고**,
소재를 고르는 곳이 두 군데(파이프라인 첫 열 · 소재 탭)로 갈라져 있었다. 전수 검사 후 재설계.

### 오너 개입 지점은 딱 3곳

```
[소재 발굴]─── 게이트① 진행 / 반려(+이유) / 보류(+이유)   ← 이유가 학습된다
     ↓ ▶ 진행 (ideas.json 에 stage:1)
[기획안]────── 게이트② 방향 확인 / 수정지시
     ↓
[제작·검수]─── 개입 없음 (결정적 코드 + 자동 검수)
     ↓
[승인대기]──── 게이트③ 🚀발행 / ✏️수정지시 / ❌반려   ← 카드 실물+캡션+검수를 보고 결정
     ↓ 승인
[발행]──────── data/publish-queue.md (오너 승인 없이는 아무것도 안 들어옴)
     ↓
[성과]──────── data/performance.md → 다시 게이트①의 판단 재료
```

### 화면 변경

| 변경 | 이유 |
|---|---|
| 첫 탭 = **🔔 오늘**(결정함) | 접속 즉시 "내가 결정할 것"만 본다. 없으면 "없음"이라고 말해 앱을 닫게 한다 |
| 연결 상태 → **제목 행 우측 뱃지** | 한 번 연결하면 볼 일 없는 정보가 한 줄을 차지하고 있었다 |
| 파이프라인 **마이닝 열 제거** | 소재 고르기는 💡소재 탭 단일 창구. 칸반은 '기획안'부터 |
| 워크플로 버튼(로고·평균연봉) 제거 | 오너가 누를 일도, 눌러서 이해할 결과도 없는 개발용 버튼 |
| 미연결 시 **조작 UI 잠금**(`.locked`) | 눌렸다가 실패하는 것보다 안 눌리고 이유를 말하는 게 낫다 |
| 발행 승인 = **카드 캐러셀 + 캡션 전문 + 검수 결과** | 타임라인을 읽고 짐작하는 게 아니라 나갈 물건을 보고 결정 |
| 반려·보류에 **이유 입력** | 이유 없는 거절은 회사를 학습시키지 못한다 |
| 모바일 = 칸반 세로 아코디언 | 오너는 대부분 폰으로 본다 |

### 발행 세트 (`data/review/sets.json`)

`data/content`에는 실험 렌더·중간 산출물이 섞여 있어, 전부 '승인대기'로 띄우니 **결정함이 27건**이 됐다.
→ **오너가 한 번에 승인하는 단위**를 명시하는 매니페스트를 도입. 여기 등록된 세트만 발행 후보가 된다(27 → 5).

- `cards[]` 순서 = 캐러셀 순서. 대표 장 하나가 세트 전체를 대표하는 티켓이 된다
- 캡션이 없으면 결정함에 올라오지 않는다 — 올릴 글이 없으면 결정할 게 없다
- 미등록 렌더는 `실험` 칩이 붙어 파이프라인 목록에만 남는다
