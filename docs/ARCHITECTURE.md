# 시스템 아키텍처

> ⚠️ **읽는 법(2026-08-08)**: 이 문서에서 **살아있는 것은 계약(contract)**이다 — provenance(수치는 코드가 원자료에서 추출), 결정적 렌더, 카드 JSON 필드 계약. 아래 **오케스트레이터 상태 머신·리서치/기획/편집 에이전트 노드·자동 발행은 미구현 비전**이다(요약: `docs/archive/VISION-automation.md`). 실제 제작 흐름은 `CLAUDE.md` §2를 본다.

## 1. 전체 파이프라인 *(아래 다이어그램의 에이전트 노드·자동 발행은 비전 — 위 주석 참조)*

```
                        ┌─────────────────────────────────────────────────┐
                        │              오케스트레이터 (상태 머신)            │
                        └─────────────────────────────────────────────────┘
  [매일 새벽]         [아침]           [아침]          [승인 후]         [승인 후]
┌───────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐
│  수집기     │ →  │ 리서치     │ →  │ 기획       │ →  │ 편집       │ →  │ 디자인     │
│ Collectors │    │ 에이전트   │    │ 에이전트   │    │ 에이전트   │    │ (렌더러)   │
│ (결정적 코드)│    │           │    │           │    │           │    │           │
└───────────┘    └───────────┘    └───────────┘    └───────────┘    └───────────┘
  raw JSON         소재 후보 10건    기획안 3~5건      템플릿 JSON       PNG 1080×1350
                                       │                │                │
                                  ┌────▼────┐      ┌────▼────┐     ┌────▼────┐
                                  │ 게이트 1 │      │ 팩트체크 │     │ 디자인QA │
                                  │ 기획 승인 │      │ 에이전트 │     │ 에이전트 │
                                  │ (사람)   │      │ (자동)   │     │ (자동)   │
                                  └─────────┘      └─────────┘     └────┬────┘
                                                                        │
                                                   ┌───────────┐   ┌────▼────┐
                                    Instagram  ←   │ 발행       │ ← │ 게이트 2 │
                                    Graph API      │ 스케줄러   │   │ 최종 승인 │
                                                   └─────┬─────┘   │ (사람)   │
                                                         │         └─────────┘
                                                   ┌─────▼─────┐
                                                   │ 인사이트    │ → 주간 성과 분석 → 기획 에이전트 가중치 갱신
                                                   │ 수집       │
                                                   └───────────┘
```

**원칙: 사람이 서는 곳은 게이트 1(기획 승인)과 게이트 2(발행 승인) 딱 두 곳.** 나머지 검증은 자동(팩트체크, 디자인 QA)이다. 신뢰가 쌓이면 게이트 1을 "자동 승인 + 사후 통보"로 낮춰 개입을 더 줄일 수 있다.

## 2. 데이터 흐름과 계약 (Contracts)

파이프라인의 각 단계는 **파일(JSON)로 대화**한다. 에이전트를 갈아끼워도 계약만 지키면 파이프라인이 돈다.

```
data/
├── raw/2026-07-18/           # 수집기 출력 (소스별 정규화 JSON)
│   ├── ecos-base-rate.json
│   ├── molit-apt-trades.json
│   └── news-headlines.json
├── briefs/2026-07-18.json    # 리서치 에이전트 출력: 소재 후보 목록
├── plans/2026-07-18/         # 기획 에이전트 출력: 건별 기획안
│   └── plan-001.json
├── content/2026-07-18/       # 편집 에이전트 출력: 템플릿 데이터 (렌더 입력)
│   └── content-001.json      #   → templates/{format}/schema.json 을 만족해야 함
└── out/2026-07-18/           # 렌더 출력
    ├── content-001-p1.png
    └── content-001-meta.json # 캡션, 해시태그, 예약 시각, 출처
```

### 핵심 계약: 콘텐츠 JSON (렌더 입력)

```jsonc
{
  "template": "ranking-table@1",       // 템플릿 ID + 버전
  "date": "2026-07-18",
  "title": "국내 10대 건설사 연봉 순위",
  "subtitle": "시공능력평가 상위 10개사 연봉 비교",
  "source": { "name": "각 사 2025년 사업보고서", "asOf": "2026-07-17" },
  "items": [
    { "rank": 1, "name": "삼성물산", "logo": "samsung-cnt", "value": "1.28억", "sub": "15.4년" }
  ],
  "provenance": {                       // 팩트체크용: 모든 수치의 출처 좌표
    "items[0].value": "raw/2026-07-18/dart-salary.json#/삼성물산/avgSalary"
  }
}
```

`provenance` 필드가 핵심 장치다: 편집 에이전트는 모든 수치에 대해 raw 데이터의 출처 경로를 남겨야 하고, 팩트체크는 이 경로를 따라 **코드로** 원본과 대조한다. 출처 없는 수치 = 자동 반려.

## 3. 기술 스택

| 레이어 | 선택 | 이유 |
|---|---|---|
| 언어/런타임 | TypeScript + Node.js (모노레포: pnpm workspace) | 렌더러(Playwright)·API·대시보드를 한 언어로 |
| 수집기 | Node cron 잡 (+ 필요 시 Python 크롤러) | 공공 API는 대부분 REST/XML |
| LLM | Claude API — 기획·리서치·편집: 상위 모델, 라벨링·캡션 등 단순 작업: Haiku | 단계별 비용 최적화 |
| 에이전트 프레임워크 | Claude Agent SDK (또는 직접 tool-use 루프) | 파일 계약 기반이라 프레임워크 의존 낮음 |
| 렌더링 | HTML/CSS 템플릿 + Playwright 스크린샷 | 픽셀 단위 재현성, 웹 기술로 무한 커스텀 |
| 차트 | 서버사이드 ECharts/D3 → 템플릿에 SVG 삽입 | 참고 계정 수준의 커스텀 차트 |
| DB | SQLite → 성장 시 Postgres | 파이프라인 상태·발행 이력·성과 지표 |
| 큐/스케줄 | cron + 오케스트레이터 상태 머신 (BullMQ는 규모 커지면) | 하루 수십 건 규모엔 단순함이 정의 |
| 대시보드 | Next.js (승인 UI) + Slack/Telegram 봇 (모바일 승인) | 아침 침대에서 승인 가능해야 함 |
| 발행 | Instagram API with Instagram Login (Content Publishing) | **페이스북 페이지 불필요**, 내 계정 전용이라 앱 심사 없이 개발 모드로 동작. 장기 토큰 60일 + 자동 갱신 |
| 인프라 | VPS 1대 or Fly.io/Railway + S3호환 스토리지 | 월 $10~20 수준에서 시작 |
| 관측 | 파이프라인 로그 DB + Slack 알림 + LLM 비용 미터링 | 장애·비용 조기 감지 |

## 4. 오케스트레이터 상태 머신

콘텐츠 1건의 생애주기:

```
DRAFT(기획안) → APPROVED_PLAN → EDITING → FACT_CHECK → RENDERING → DESIGN_QA
    → REVIEW(게이트2) → SCHEDULED → PUBLISHED → MEASURED
반려 경로: 어느 단계든 → REJECTED(사유 기록) 또는 → REVISION(자동 재시도, 최대 2회)
```

- 상태 전이는 전부 DB에 기록 → 대시보드 칸반이 이 테이블을 그대로 보여줌
- 자동 재시도 2회 실패 시 사람에게 에스컬레이션 (Slack 알림)
- 매일 발행 슬롯(예: 오전 11시, 저녁 7시)이 비어 있으면 콘텐츠 뱅크(에버그린 재고)에서 자동 충원

## 5. 비용 추정 (일 3건 발행 기준, 대략)

| 항목 | 월 비용 |
|---|---|
| LLM API (리서치·기획·편집·QA, 일 3건 + 브리핑) | $30~80 |
| 서버 (VPS/Fly.io) + 스토리지 | $10~25 |
| 데이터 소스 | 공공 API 무료, 유료 프록시/크롤링 툴 쓰면 +$0~50 |
| **합계** | **월 $40~150 수준** |

콘텐츠 1건당 원가 ≈ $0.5~1.5. 사람이 직접 만들 때 대비 압도적으로 낮고, 발행량을 늘려도 한계비용이 거의 늘지 않는 구조가 목표.

## 6. 확장 포인트

- **멀티 계정**: 계정별 설정 파일(니치, 템플릿 셋, 발행 캘린더, 톤)만 추가 — 파이프라인 코드는 공유
- **릴스**: 동일 콘텐츠 JSON → Remotion(React 기반 영상 렌더링)으로 모션그래픽 자동 생성
- **다국어**: 편집 에이전트에 번역 단계 추가 → 영어권 계정 동시 운영
