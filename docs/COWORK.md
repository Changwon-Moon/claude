# 🏠 Cowork 이전 안내 — 이 공장을 코워크로 옮겨 심기

> **읽는 사람**: 오너, 그리고 코워크에서 이 저장소를 처음 여는 Claude 세션
> **한 줄 요약**: 옮길 것은 거의 없습니다. **팀의 기준과 역량은 이미 저장소 안에 문서로 있고,
> 그걸 읽는 주체가 창구를 따라올 뿐**입니다. 진짜 해야 할 일은 "매 세션 어떻게 시작하나" 하나입니다.

*(2026-07-31 코워크에서 백지 clone 으로 실측하며 작성)*

## §1. 먼저 — "팀은 유지되는가"에 대한 정직한 답

**유지됩니다. 다만 이유가 오너가 생각하시는 것과 다를 수 있어 그것부터 밝힙니다.**

저장소를 뒤져 확인한 사실입니다:

| 팀 관련 자산 | 어디에 | 지금 상태 |
|---|---|---|
| 사원카드(가치관·책임·학습로그) | `company/teams/*.md` 9팀 | 문서 |
| 팀별 시스템 프롬프트 | `prompts/*.md` 9팀 | **초안 v0 — 실행하는 코드 없음** |
| 오너 판단 원칙 | `company/CEO.md` 103개 | 문서 |
| 조직도·6축 루브릭 | `docs/AGENTS.md` | 문서 |
| 편집 에이전트(M6)·리서치 기획 에이전트(M7) | — | **⬜ 대기 (미구축)** |
| 실제로 LLM 을 호출하는 코드 | `packages/pipeline/src/review/llmReview.ts` | 이거 하나뿐 (검수용, 키 있을 때만) |

`prompts/` 를 참조하는 코드는 **관제탑이 화면에 표시하는 파서**와 **빠진 파일을 채우는 스캐폴더**
둘뿐입니다. 프롬프트를 읽어 에이전트를 돌리는 러너는 아직 없습니다.

**그래서 지금 "팀"이란 = Claude 세션이 작업 전에 읽는 기준 문서 묶음입니다.**
9명의 봇이 상주하는 게 아니라, 한 세션이 그때그때 해당 팀의 모자를 쓰는 구조입니다.

이게 **좋은 소식**인 이유: 옮길 실행 자산이 없으니 **이식 실패가 원천적으로 불가능**합니다.
저장소를 clone 하는 순간 `CLAUDE.md` → 세션 규칙, `CARD_CHECKLIST.md` → 제작 기준,
`CEO.md` 103개 원칙, `AGENTS.md` 6축 루브릭이 **전부 그대로 상속**됩니다.
창구를 바꾼다고 사라질 수 있는 건 애초에 하나도 없습니다.

> 뒤집어 말하면 — **팀의 역량을 올리는 일은 창구 이전과 무관합니다.**
> 그건 M6·M7 을 짓거나 `prompts/` 를 다듬는 일이고, 코워크에서든 클로드 코드에서든 똑같이 합니다.

## §3. 클로드 코드와 코워크의 진짜 차이 — 딱 두 가지

기술적으로는 둘 다 같은 일을 합니다. 운영에서 갈리는 건 두 개뿐입니다.

### ① 작업 공간이 매번 새로 생긴다

코워크 세션은 임시 컨테이너에서 돕니다. 세션이 끝나면 반납됩니다.
→ **매 세션 clone 부터 시작**하고, **커밋하지 않은 작업은 사라집니다.**

겁낼 일은 아닙니다. `CLAUDE.md` 가 이미 "커밋 안 한 작업은 세션과 함께 사라진다"고
규정하고 있어서, **원래 지키던 규칙이 더 엄격하게 강제될 뿐**입니다.
오히려 좋은 점이 큽니다 — 오늘 발견한 "백지에서만 드러나는 구멍" 같은 게
매번 자동으로 걸러집니다. 재현성이 습관이 아니라 구조가 됩니다.

### ② 오너가 자리에 없어도 돌아간다

폰을 닫아도 작업이 계속되고, **스케줄을 걸어 무인으로 돌릴 수 있습니다**(§6).
"자동화"라는 이름으로 대화를 만드셨던 그 목적에 실제로 닿는 부분입니다.

## §4. 무엇을 어디서 돌리나 — 경계선

이전한다고 전부 코워크로 들어오는 게 아닙니다. **이미 GitHub 에서 도는 것은 그대로 둡니다.**

| 층 | 어디서 | 이전 영향 |
|---|---|---|
| 정기 데이터 수집 (`reb`·`molit`·`dart`·`kr-market`) | **GitHub Actions cron** | 없음 — 키가 Secrets 에 있고 거기서 돈다 |
| 관제탑 배포 (`tower-deploy`) | **GitHub Actions → Cloudflare** | 없음 |
| 완성본 보관 (`publish-archive`) | **GitHub Actions** | 없음 |
| 소재 자동 수집 (`research-digest`, 매일 07:00 KST) | **GitHub Actions cron** | 없음 |
| 카드 제작 — 빌더 작성·렌더·검수·캡션 | **코워크(작업 세션)** | ← 여기가 이전 대상 |
| 소재 발굴·판단, 기준 문서 갱신, 학습 기록 | **코워크(작업 세션)** | ← 여기가 이전 대상 |
| 승인·인스타 업로드·성과 기입 | **오너** | 없음 (자동 발행 안 함) |

**즉 이전 대상은 "판단과 제작"뿐이고, 배관은 건드리지 않습니다.**
관제탑 버튼이 Actions 를 부르는 구조도 그대로 삽니다.

## §5. 오너가 해야 할 일 — 체크리스트

### 5-1. 저장소 접근 (필수, 매 세션)

코워크 세션은 매번 새 컨테이너라 GitHub 인증이 남지 않습니다. 세션마다 토큰이 필요합니다.

- GitHub → Settings → Developer settings → **Fine-grained tokens**
- 대상: **이 저장소 하나만** / 권한: **Contents: Read and write** (푸시하려면 write 필요)
- 만료: 짧게 쓰고 폐기하거나, 자주 쓰실 거면 **30~90일**로 두고 만료일을 달력에 적어두기

> ⚠️ **토큰은 절대 저장소에 커밋하지 않습니다**(`CLAUDE.md` 절대 규칙).
> 채팅에 붙여넣는 것은 그 세션 안에서만 쓰이고 컨테이너와 함께 폐기됩니다.

### 5-2. 세션 시작 한 줄 (필수)

새 코워크 대화를 열고 이 한 줄을 붙여넣으면 됩니다:

```
github.com/Changwon-Moon/claude (브랜치 claude/instagram-content-automation-roadmap-fxnb7p)
clone 해서 docs/HANDOFF.md 읽고 doctor 돌려줘. 토큰: <여기에 토큰>
```

세션이 알아서 clone → `pnpm install` → `doctor.mjs` 까지 하고 ✅/❌ 를 보고합니다(2분 내외).
✅ 가 뜨면 그때부터 평소처럼 지시하시면 됩니다.

### 5-3. API 키 (선택 — 지금은 안 해도 됨)

`doctor` 의 B등급 경고 5건은 **새 데이터를 수집할 때만** 필요합니다.
기존 `data/datasets/` 로 카드는 그대로 나옵니다.

| 키 | 어디에 두나 | 필요할 때 |
|---|---|---|
| `RONE`·`MOLIT`·`DART`·`ECOS` | **GitHub Secrets** | 정기 수집(Actions 가 씀) — 코워크엔 불필요 |
| `ANTHROPIC_API_KEY` | 코워크 세션에 붙여넣기 | 작업 세션에서 LLM 검수까지 돌리고 싶을 때만 |

> 코드 검수(결정성·레이아웃·캡션 린트·수치 대조)는 **키 없이 동작**합니다.
> 오보 0 을 지탱하는 네 가지(렌더·designQa·md5 회귀·빌더 가드)는 전부 키가 필요 없습니다.

### 5-4. 창구를 정리한다 (중요)

**렌더를 두 곳에서 번갈아 하지 않습니다.** 결정적 렌더의 전제가 "같은 기계"입니다.
코워크로 옮기기로 하셨으면 카드 렌더는 코워크(또는 Actions)에서만 합니다.
`HANDOFF.md` §12 의 "두 창구로 쪼개지 말라"가 픽셀 층에도 그대로 적용됩니다.

## §6. 옮긴 다음에 새로 열리는 것 — 스케줄 자동화

여기가 클로드 코드에 없던 부분입니다. 다만 **이미 Actions cron 이 하는 일과 겹치지 않게** 나눕니다.

| 성격 | 어디에 맡기나 | 예 |
|---|---|---|
| 정해진 API 를 정해진 시각에 긁기 | **Actions cron** (이미 있음) | 부동산원 지수, 실거래, 증시 |
| **판단이 필요한 일** | **코워크 스케줄** (새로 열리는 것) | 소재 후보 추리기, 초안 캡션, 주간 리포트 |

코워크 스케줄이 잘 맞는 예:

- 매주 월요일 아침 — `research/ideas.json` 대기 55건에서 **이번 주 후보 3건을 6축 루브릭으로 추려 보고**
- 매월 5일(국토부 갱신일) 이후 — **정기물 카드 재생산 → 검수 → 결재 대기까지 올려두기**
- 발행 후 — 성과 기입 리마인드

> 무인으로 도는 것은 **승인 앞까지만** 입니다. 발행은 오너가 직접 합니다(§4, 자동 발행 폐지 결정 유지).

## §7. 권하는 순서 (한 번에 다 하지 않아도 됩니다)

1. **1주차 — 병행.** 코워크에서 카드 1~2장을 실제로 만들어 보고, 왕복 횟수가 줄어드는지 봅니다.
   (클로드 코드가 남긴 판단 기준 그대로: *"다음 카드를 한 장 만들어 보고, 왕복이 12번에서
   2~3번으로 줄어드는지 보세요"*)
2. **2주차 — 렌더 창구 단일화.** 만족스러우면 카드 렌더를 코워크로 고정합니다.
3. **3주차 — 스케줄.** 소재 발굴 정기 실행을 하나만 걸어보고, 결과물이 쓸 만한지 봅니다.
4. **그 다음 — 역량.** M6·M7(에이전트 구축)이나 `prompts/` 다듬기.
   이건 창구와 무관한 별개 트랙입니다(§1).

각 단계마다 **되돌릴 수 있습니다.** 자산이 저장소에 있으니 창구는 언제든 바꿔 달 수 있습니다.

## §N. 코워크 세션에서 데이터 수집 — "안 된다" 하지 말고 push-트리거 (2026-07-31 오너 지시)

**원칙: 코워크 세션은 국토부·부동산원 등 외부 API 를 직접 못 부른다(망 차단·키는 Secrets). 그리고 GitHub API(workflow_dispatch)도 이 세션에선 403 이다. 하지만 `git push` 는 된다.**

그래서 수집이 필요하면 **"안 된다"고 답하지 말고** 다음을 한다:

1. `data/collect-request.json` 에 수집할 지역·월을 적는다. 형식:
   ```json
   { "jobs": [
       { "region": "seoul",    "gu": "강남구,서초구",                       "months": "202607" },
       { "region": "gyeonggi", "gu": "성남시분당구,용인시수지구,수원시영통구", "months": "202607" }
     ], "force": false }
   ```
   (구 이름은 `packages/collectors/src/data/lawd-{seoul,gyeonggi}.json` 의 `codes` 키와 정확히 일치해야 한다.)
2. **push 한다.** `.github/workflows/collect-on-request.yml` 이 이 파일 변경을 감지해 자동으로
   `molitCli` 를 돌리고 `data/datasets/molit/*.json` 캐시를 커밋한다. (파인그레인드 토큰 push 는 워크플로를 트리거한다 — GITHUB_TOKEN push 와 달리.)
3. 수집이 끝나면(수 분) **`git pull` 로 새 캐시를 받는다.** Actions 실행 상태 조회는 API 라 막혀 있으니, 상태는 보지 말고 pull 로 결과만 확인한다.

**즉, "이 세션에서 07월 수집 못 한다"는 틀린 답이다.** 정답은 "요청 파일에 적어 push하면 Actions 가 수집한다"이다.
정기 수집(매월 5일)·수동 dispatch(`molit-collect.yml`)는 그대로 두고, 세션발(發) 요청은 이 push-트리거를 쓴다.
