## 한 줄 요약

**청약홈과 실거래는 같이 죽었지만 원인이 다르다.**
실거래는 **키가 멀쩡하고 연결이 실행마다 갈리는** 문제, 청약홈은 **인증이 100% 거부되는** 문제다.
덤으로, 실거래 쪽은 며칠째 죽어 있는데 **Actions 가 초록불**이었다는 구조적 결함을 찾아 고쳤다.

---

## 1. 실거래(오늘의 신고가) — 키 문제가 **아니다**

결정적 증거. 같은 키·같은 인자(`--months 2`)로 **28분 안에** 성공→실패→성공:

| 실행(UTC) | 방아쇠 | 결과 |
|---|---|---|
| 08-12 23:14 | push | ✅ 수집 성공 **122회** / 실패 0회 |
| 08-12 23:34 | push | ❌ 수집 성공 0회 / 실패 **18회** |
| 08-12 23:42 | push | ✅ 수집 성공 **122회** / 실패 0회 |

키가 만료·미등록이면 20분 뒤에 성공할 수 없다. 오류도 대부분 **`fetch failed`** — HTTP 응답조차
없는, **연결 자체가 안 열린** 상태다. 08-18 한 번 나온 `HTTP 403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR`
는 공공데이터포털 게이트웨이가 막을 때 뱉는 오답 메시지로 보인다(키가 진짜 미등록이면 늘 나야 한다).

전체 판정(UTC 기준): 실패 08-12·08-14·08-17·08-18(×2) / 성공 08-12(×2)·08-13·08-15·08-16.
**대략 절반**이다.

**가장 유력한 설명**: GitHub Actions 러너의 **출구 IP 가 실행마다 달라서**, 어떤 대역은 포털
게이트웨이에 막히고 어떤 대역은 통과한다. 수집기는 이미 실행 안에서 4회 재시도 + 5×60초를
기다리지만, **같은 실행 안에서는 IP 가 안 바뀌므로** 그 기다림이 소용없다.
실제로 23:34 실패 → 23:42 성공은 **8분 뒤 다른 실행(다른 러너)** 이었다.

- 활용기간 2026-08-12 ~ 2028-08-12 · 처리상태 승인 · [운영계정] → **정상. 오너가 손댈 것 없음.**

## 2. 청약홈 수집 — 이쪽은 **진짜 인증 문제**

성격이 정반대다. 예외 없이 100% 실패한다:

| 실행(UTC) | 결과 |
|---|---|
| 08-16 03:03 | ✅ 성공 |
| 08-17 03:03 | ❌ 실패 `HTTP 401` |
| 08-18 02:58 | ❌ 실패 `HTTP 401` |
| 08-18 22:45 | ❌ 실패 `HTTP 401` (세션이 수동 실행) |

08-16까지 예외 없이 성공하다 **08-17부터 100% 실패**, 전부 `HTTP 401`. 연결은 되는데
**인증이 거부**된다 — 실거래의 `fetch failed` 와는 완전히 다른 신호다.
호스트도 다르다: 청약홈은 `api.odcloud.kr`, 실거래는 `apis.data.go.kr`.

### ⚠️ 오너가 확인할 것 (이것 하나뿐)
공공데이터포털 → 마이페이지 → 활용신청 현황에서
**`한국부동산원_청약홈 분양정보 조회 서비스`** 한 건:

- 목록에 **있는지**
- **[운영계정]인지 [개발계정]인지**
- 처리상태 · 활용기간

가설: 08-12 에 실거래를 **운영계정**으로 올리면서, **개발계정**으로 신청돼 있던 청약홈이
며칠 유예 후 끊긴 것. 08-17 이 그 무렵과 맞는다. (확인 전까지는 가설이다.)

## 5. 이번에 발견한 구조적 결함 — 초록불이 "일했다"가 아니었다

`오늘의 신고가` 는 수집이 **전부** 실패해도 종료코드 0 이라 **Actions 가 초록불**이었다.
텔레그램 본문에는 "⛔ 실거래 API 가 계속 응답하지 않아 …"가 크게 적혀 나갔지만, 그 문구는
**사람이 끝까지 읽어야** 보인다. 그렇게 다섯 번이 조용히 지나갔고, 오너가 알림을 읽고서야 물었다.

**고친 것**

1. **수집 성공 0회면 워크플로를 실패로 끝낸다.** 일부만 실패한 날은 그대로 초록불 —
   부분 실패까지 빨간불로 만들면 빨간불이 흔해져 안 읽힌다.
2. **실패한 날에도 상세 알림을 그대로 보낸다.** 워크플로의 실패 가지가 짧은 "확인 실패" 한 줄만
   보내고 있어서, 1번만 고쳤다면 **오너가 받던 원인 문구가 사라졌을 것**이다.
   수집기가 죽기 전에 써 두는 `singo-alert.txt` 를 그대로 보내도록 바꿨다.
3. **되돌려 확인** — 대기 시간을 50ms 로 낮춰 실제로 돌려 **종료코드 1** 을 확인하고
   원상복구(md5 대조). 통과만 보면 검사가 켜졌는지 알 수 없다.

## 6. 신설 — `node scripts/pipeline-status.mjs`

"지금 뭐가 멈춰 있나"를 한 화면에 보는 자리가 **없었다.** 세션은 워크플로 40개를 하나씩 뒤져야
했고, 오너는 텔레그램 본문을 읽어야 했다.

- GitHub API 를 안 쓴다 — `data/*-last.md` 와 파일 나이만 읽어 **오프라인에서도** 돈다.
- 배관마다 `daily`/`periodic`/`untilDone`/`onDemand` 를 적어 **완료라서 조용한 배관**을
  경고로 안 띄운다(첫 판이 오탐 3건을 냈다).
- 같은 키를 쓰는 배관이 함께 멎으면 "키를 의심하라"고 말해 준다.
  ⚠️ **이번 건이 바로 그 힌트의 한계다** — 실거래 4개가 함께 멎어 키를 지목했지만
  실제로는 키가 멀쩡했다. **힌트는 가설이지 판정이 아니다.**

## 이번 건의 교훈 (다음 사람에게)

**같은 증상을 하나의 원인으로 묶지 않는다.** 두 배관이 같은 주에 죽었고 둘 다 공공데이터포털이라
"키 만료"로 묶었는데, 실제로는 **연결 문제와 인증 문제**로 갈렸다. 갈라 준 것은 추측이 아니라
**실행 이력의 시각과 오류 문구**였다 — `fetch failed`(응답 없음)와 `HTTP 401`(응답 있음)은
다른 사건이고, **28분 안의 성공→실패→성공**은 어떤 키 가설도 부순다.
증상이 아니라 **신호**를 봐야 한다.
