## 2. 증상이 말해 주는 것

**`fetch failed` 는 HTTP 상태코드가 아예 없다는 뜻이다** — 연결(TCP/TLS)이 안 열린 것이다.

- ❌ 키 문제 아님 — 키 문제면 **403/401** 이 온다. 지문 `4e34245e`(64자) 정상, 회복 후 같은 키로 성공.
- ❌ 서버 오류 아님 — 그러면 **500** 이 온다.
- ❌ 우리 코드 아님 — 같은 코드가 09:41 에 122/122 성공.
- ⭕ **연결 자체가 거부/드롭됐다.** 방화벽·차단·과부하의 모양이다.

**포털 전체가 아니라 그 서비스만이었을 가능성이 높다.** 같은 호스트
(`apis.data.go.kr`)의 **건축물대장 서비스는 04:18 에 실제 데이터를 받아왔다**(공급면적 수집).
다만 3시간 앞선 시각이라 동시각 대조는 아니다.

### 아직 못 가린 것

이 세션의 컨테이너는 `apis.data.go.kr` 로 직접 못 나간다(샌드박스 차단). 그래서
**「한국 일반 회선에서도 그 시각에 닫혀 있었는지」를 확인하지 못했다.** 그게 갈리면:

- 일반 회선도 닫혔다 → **국토부/포털 쪽 점검·과부하**
- 일반 회선은 됐다 → **GitHub 러너(Azure) IP 대역 차단·스로틀** — 해외 클라우드 대역을
  조이는 공공 API 가 드물지 않다

가리는 법 둘: ⑴ 다음에 실패 톡이 오면 오너가 그 시각에 실거래가 공개시스템을 한 번 열어 본다.
⑵ 예약 시각을 07:00 → 07:40 으로 옮겨 아침 피크를 비껴가 본다.

## 4. 고친 것

### ① 재시도를 **사다리**로 — +20분 · +1시간 · +2시간 (오너 승인)

열리는 칸에서 멈춘다. 08-24 의 실제 회복 시간이 1시간 17분이었는데
11분 뒤 한 번만 두드린 것은 **같은 주사위를 너무 빨리 다시 굴린 것**이었다.

⚠️ 「바로 한 번」 칸은 **일부러 뺐다** — 08-26 에 11분 뒤 자동 재시도가 원 런과 똑같이
무너졌다. 아침에 문이 닫히면 몇 분으로는 안 열린다. 되살리려면 그 실측부터 다시 본다.

⚠️ **중간 칸의 실패는 조용하다**(`quiet: true`). 안 그러면 아침에 ⛔ 가 네댓 통 쌓인다 —
08-26 에 실제로 다섯 통이 갔다(예약·자동재시도 2통 + 세션이 손으로 돌린 3통).
말하는 것은 **첫 실패와 마지막 칸** 둘뿐이고, **성공은 언제나 보낸다.**
⚠️ 조용히 넘어간 칸도 `data/singo-last.md` 에는 남는다 —
**말을 안 하는 것과 기록을 안 남기는 것은 다르다.**
⚠️ 마지막 칸 실패 문구에 「못 받은 신고가는 사라지지 않는다」를 붙였다.
실패 톡이 걱정만 남기면 안 된다.

### ② 🔴 연결 실패가 재시도를 **한 번도 안 하고 있었다**

`molit.ts` 의 `fetchPage` 는 3회 백오프를 도는데, `getRaw` 가 **예외를 던지면**
(=`fetch failed`) 그 루프를 그대로 빠져나갔다.
**HTTP 500 은 3번 두드리고, 연결 실패는 1번** — 정확히 거꾸로다.
백오프가 필요한 쪽은 「답은 왔는데 500」보다 「연결이 안 열림」이다.
이제 둘 다 3번 두드린다(401·403 은 그대로 즉시 포기 — 키 문제는 두드려도 안 열린다).

### ③ 손으로 돌린 실패 톡에 꼬리말이 없었다

`workflow_dispatch` 실패는 「재시도합니다」도 「여기까지입니다」도 안 붙어서,
오너 입장에선 ⛔ 만 뜨고 누가 왜 돌렸는지 알 수 없다. 이제 그 사실을 적는다.

### ④ 주차대수 워크플로의 **거짓 초록불**

08-26 07:44 실행이 "성공"인데 로그 25줄이 전부 `⏭ 이미 있음` — **네트워크를 한 번도 안 탔다.**
하마터면 "주차대수는 성공했으니 포털은 살아 있다"로 읽을 뻔했다.
이제 실제로 받아 본 건수를 세어 적고, 0이면
「이 초록불은 API 가 살아 있다는 증거가 아닙니다」를 남긴다.
**고친 것은 동작이 아니라 기록이다** — 건너뛰는 것 자체는 정상이다.
