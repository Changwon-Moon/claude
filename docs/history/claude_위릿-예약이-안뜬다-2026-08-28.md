# 깃허브 예약이 안 뜬다 — 파수꾼을 밖으로 (2026-08-28)

## 한 줄

**이틀 연속** 아침 신고가 톡이 안 왔다. 실패가 아니라 **실행이 안 생겼다.**
어제 세운 파수꾼도 같이 안 떠서 **아무도 말하지 않았다.**

---

## 1. 숫자로 본 것 — 자주 걸수록 더 많이 버려진다

**48시간 실측** (2026-08-26 02:00 ~ 08-28 02:00 UTC)

| 워크플로 | 주기 | 기대 | 실제 | 실행률 |
|---|---|---:|---:|---:|
| 예약 파수꾼 | 매시간 | 48 | 2 | **4%** |
| 주차대수 | 2시간마다 | 24 | 12 | 50% |
| 공급면적 | 2시간마다 | 24 | 13 | 54% |
| **오늘의 신고가** | 하루 1회 | 2 | 0 | **0%** |
| 소재 보드 · 파이프라인 | 하루 1회 | 2 | 0 | **0%** |

깃허브 문서가 말하는 그대로다 — 예약은 best effort 이고 「짧은 간격을 피하라」.
같은 기간 상태 페이지에 Actions 장애 세 건(8/24 · 8/26 · 8/26~27)이 올라와 있었지만,
08-27 21:00 이후로는 **장애가 해소됐다고 적힌 뒤에도** 계속 버려졌다.

## 2. 🔴 어제 세운 파수꾼이 **먼저 죽었다**

08-27 에 「예약이 안 뜬 것을 찾는」 파수꾼을 매시간으로 걸었다. 48번 중 **2번** 돌았다.
08-28 아침에는 신고가도 안 뜨고 파수꾼도 안 떠서 결국 오너가 먼저 알아챘다.

**감시자를 감시 대상과 같은 곳에 두면 같이 가라앉는다.**
깃허브 예약을 깃허브 예약으로 감시하는 것은 같은 배 안에서 그 배에 구멍이 났는지 보는 것이다.

⚠️ 그리고 어제의 고침 방향 자체가 문제를 **키웠다** — 촘촘히 볼수록 안전해진다고 생각했는데,
이 인프라에서는 촘촘할수록 **먼저 버려진다.** 직관과 반대다.

## 3. 안전망을 두 겹으로

### ① 저장소 안 — `schedule-watchdog.yml` (간격을 벌렸다)

매시간 → **08:40 · 09:40 · 11:40 KST** 세 번.
⚠️ **매시간으로 되돌리지 않는다.** 되돌리고 싶으면 위 표의 4% 부터 다시 본다.

### ② 저장소 밖 — 코워크 예약 작업 (진짜 안전망)

**매일 08:40 KST**, 앤트로픽 인프라에서 돈다. 깃허브 스케줄러와 완전히 독립이다.
`trig_01TFiYm3myMtVuUqJa95s5bC`

1. 클론하지 않고 API 로 `data/singo-last.md` 만 읽는다
2. `- 실행:` 날짜가 오늘(KST)이 아니면 `singo-daily.yml` 을 `workflow_dispatch` 로 띄운다
3. 오너에게 알린다 → 10~15분 뒤 결과 확인 → 실패면 40분 뒤 한 번 더

⚠️ **정상인 날엔 아무 말도 안 한다.** 매일 아침 「이상 없습니다」가 오면 곧 안 읽게 된다.
⚠️ 카드를 만들거나 커밋하지 않는다 — **띄우고 알리는 것**까지가 이 작업의 일이다.

## 4. 오너가 손으로 할 수 있는 것

| 하고 싶은 것 | 어디 |
|---|---|
| 오늘 신고가를 지금 돌린다 | Actions → **오늘의 신고가 (daily)** → Run workflow (기본값 그대로) |
| 실거래 API 가 열렸는지만 본다 | Actions → **실거래 문 열렸나** → 30초 뒤 톡 |

⚠️ 손으로 돌린 런에는 **자동 재시도 사다리가 안 붙는다**(톡 꼬리말에 그렇게 적힌다).

## 5. 다음 세션이 볼 것

1. **예약 시각 분산** — 일일 예약 다섯 개가 21:00~22:10 UTC 한 시간에 몰려 있다.
   한 창이 덮이면 통째로 사라진다. 정각을 피해 흩어 놓는 것을 오너와 상의할 것

3. 코워크 파수꾼이 **실제로 도는지** 며칠 지켜볼 것 — 08-29 아침이 첫 실전이다
