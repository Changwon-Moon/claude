# 🔥 오늘의 신고가 — 알림 기준

> **이 문서가 있는 이유** (2026-08-12 오너)
> "오늘의 신고가 거래 라는 새로운 위릿카드 템플릿을 만들고자 해. 그에 앞서, 매일 아침
> 텔레그램으로 청약/분양단지에 대해 알림톡 받고 있는데, 이걸 신고가 톡도 받을 수 있도록
> 먼저 세팅해줘."
>
> 카드보다 **알림이 먼저**다. 매일 무엇이 몇 건 올라오는지 며칠 봐야 카드에 담을 것이 정해진다.
> 이 문서는 그 알림이 무엇을 재고 무엇을 안 재는지의 정본이다.

## 1. 오너가 정한 것 (2026-08-12, 같은 날 한 번 좁혔다)

레퍼런스: `theflow.daily` 「주목할 만한 오늘의 실거래 — 잠실 리센츠 33평 36.95억」

| 항목 | 결정 | 왜 |
|---|---|---|
| 기준선의 범위 | **2020-01 ~ 현재** | 최고가 인덱스가 실제로 훑은 구간(`molit-peak/_progress.json` `from:202001`). ⚠️ 2006-01 이 아니다 — 그래서 카드·알림에 **"역대"라고 쓰지 않는다.** 2020년 이후 기준이라고 적는다 |
| 판정 단위 | **단지 + 전용 59타입 / 전용 84타입** | 처음엔 평형대(20·30·40평대)로 묶었다가 오너가 **"평형대 X, 평형. 전용 59·84 두 타입만"** 으로 좁혔다 |

| 단지 | **1000세대 이상 명부 안에서만** | "리스트업 해놓고 그 안에서 신고가 발생하는지만 트래킹" |

| 정렬 | **거래가 큰 순** | 갱신폭 순으로 세워 봤더니 상위가 소형·저가 단지였다. 레퍼런스 카드가 말하는 소식은 그쪽이 아니다 |
| 시각 | **04:55 KST 예약** (2026-08-31 변경) | 08-27 부터 예약 지연이 114~477분으로 튀어 앞당겼다. 늦어도 아침 안에 도착하고, 청약 알림(10:00)까지 5시간 여유가 있다 |
| 수집 창 | **최근 2개월**(이번 달 + 지난달)의 **계약월** | 실거래 신고기한이 계약 후 30일이라, 1개월만 보면 **8월 후반에 드러나는 7월 계약분이 통째로 빠진다.** ⚠️ 2026-08-19~24 에 실제로 그랬다(§9) |
| 알림에 담는 것 | **그날 새로 드러난 건만** | 수집 창은 2개월이지만 알림은 **오늘 처음 인덱스를 넘어선 건**만 싣는다. 이미 알던 거래는 다시 안 나온다 — 두 가지가 헷갈리기 쉬운데, **훑는 범위**와 **말하는 범위**는 다르다 |
| 기준을 정하는 곳 | **이 문서 + 워크플로 기본값** | 예약 런과 자동 재시도는 `data/singo-queue.txt` 를 **읽지 않는다**(2026-08-24). 대기열은 사람이 지금 한 번 돌릴 때만 쓰는 손잡이다 |

⚠️ **"돌파"는 금액대가 아니다.** 한 번 금액대(그 거래가 속한 구간)로 묶어 내보냈다가
오너가 바로 잡아냈다 — *"10억을 돌파한 단지들만 보고싶다니까. 왜 14억 11억 이런게 왜나오냐고"*.
14억 거래는 **이미 예전에 10억을 넘긴 단지**라 돌파가 아니다. 돌파는 *직전 최고가가 선 아래였는데
이번에 넘었다*는 뜻이고(9.8억 → 10.3억 = 10억 돌파), 판정은 오직 `milestoneCrossed()` 가 한다.
그래서 전체 목록에는 **금액대 제목을 아예 붙이지 않는다** — 붙이면 또 돌파로 읽힌다.
본문은 `parse/singo.ts` 의 `alertBody()` 가 만들고, 셀프테스트 10개가 이 경계를 붙잡고 있다.

## 3. "신고가"의 정의 — 코드가 재는 것

한 거래가 아래를 **전부** 만족할 때만 신고가로 부른다.

1. **1000세대 이상 명부**(`data/datasets/apt-universe.json`)에 있는 단지다
2. 전용면적이 **59타입(56~62㎡)** 또는 **84타입(82~85.5㎡)** 이다
3. 같은 **구 + 법정동 + 단지명 + 타입** 칸에서 **2020-01 이후 모든 거래**보다 비싸다
4. 그 칸에 **역대 기록이 실제로 채워져 있다** (기준선 수집이 끝난 지역)
5. **해제(취소) 거래가 아니다**
6. **중개거래다** (직거래 제외)

### 타입 폭을 둔 이유

같은 "84타입"이라도 신고 값이 84.97 · 84.99 · 83.53 처럼 흔들린다(A/B/C 타입).
한 단지 안에서 이들은 같은 평형으로 거래·호가되므로 한 칸으로 묶는다.
묶으면 문턱이 올라가는 쪽(=보수적)이라 오보를 만들지 않는다.

### ⚠️ '00평'은 환산값이다

국토부 실거래에는 **전용면적만** 들어 있다. '33평'은 공급면적 기준이고, 공급면적은 단지별
전용률(보통 72~80%)에 달려 있어 자료에 없다. 그래서 표기는 관용 환산이고 **단지에 따라
±1평 어긋날 수 있다** — 잠실 리센츠는 전용 84.99를 33평으로 부른다(2008년 준공이라 전용률이 높다).
우리는 34평으로 적는다. 원본 전용면적은 `singo-latest.json` 에 그대로 남는다.
표기를 바꾸려면 `parse/singo.ts` 의 `PYEONG_LABEL` 한 줄만 고친다.

## 4. 일부러 판정하지 않는 것 — 그리고 그 이유

| 안 하는 것 | 왜 |
|---|---|
| 기준선이 안 찬 지역 | 반쪽 기준으로 "역대 최고가"라 부르면 그게 곧 **오보**다. 초기 수집이 끝날 때까지 건너뛰고, 건너뛴 사실을 `singo-latest.json` 에 남긴다 |
| 명부에 없는 단지 | 1000세대 미만이거나 아직 세대수를 확인 못 한 곳. 이름이 애매해 명부와 못 붙이면 **추측해서 붙이지 않는다** |
| 전용 59·84 이외 평형 | 오너 결정. **리센츠 48평 신고가는 안 잡힌다** — 알고 안 잡는 것이다 |
| 역대 기록이 없는 칸의 첫 거래 | "첫 거래 = 신고가"는 사실이 아니다 |
| 직거래 | 특수관계인 거래가 섞여 시세로 읽기 어렵다. **다만 인덱스에는 넣는다** — 기록에서 빼면 직거래로 세워진 고점을 모르고 신고가라 부르게 된다 |
| 같은 금액 재거래 | 기록은 **최초로 그 값에 닿은 거래**다 |

## 5. 배관 — 준비가 두 갈래다

```
 달력 10:20 KST ──▶ apt-universe.yml            단지목록 + 세대수 → 1000세대 이상 명부
                    (다 차면 스스로 조용해짐)     data/datasets/apt-universe.json
                                                         │
 달력 11:40 KST ──▶ molit-peak-backfill.yml               │  2006-01~지난달을 나눠 훑어
                    (다 차면 스스로 조용해짐)               │  단지+타입별 역대 최고가만 남긴다
                                                         │
 달력 04:55 KST ──▶ singo-daily.yml ◀─────────────────────┘
                    ① 최근 2개월 신고분 수집
                    ② 명부 ∩ 전용59·84 ∩ 중개거래
                    ③ 역대 인덱스와 대조 → 넘어선 것만
                    ④ 인덱스 갱신(내일의 기준)
                    ⑤ 텔레그램 (0건인 날도 한 줄)
```

**두 초기 수집은 서로 안 잡아먹는다.** 공동주택 서비스(명부)와 실거래 서비스(인덱스)는
공공데이터포털에서 **다른 서비스**라 트래픽 한도를 따로 센다.

| 파일 | 무엇 |
|---|---|
| `data/datasets/apt-universe.json` | **1000세대 이상 명부.** 오늘 무엇을 보고 있는지 눈으로 볼 수 있다 |
| `data/datasets/apt-list/{lawdCd}.json` | 시군구별 공동주택 단지 목록 |
| `data/datasets/apt-hhld.json` | 단지코드 → 세대수 캐시. `hhld: 0` = 조회했으나 값 없음(다시 안 두드린다) |
| `data/datasets/molit-peak/{lawdCd}.json` | 역대 최고가 인덱스. `meta.doneMonths` 가 진행 상황의 **유일한 진실** |
| `data/datasets/molit-peak/_progress.json` | 초기 수집이 얼마나 남았나 |
| `data/datasets/singo-latest.json` | 오늘 판정 결과 전건 (**카드 빌더가 읽을 곳**) |
| `data/singo-alert.txt` | 텔레그램 문구 (0건이면 빈 파일 → heartbeat 로 대체) |
| `data/singo-last.md` · `data/apt-universe-last.md` | 마지막 실행 로그. **"안 왔는데?" 싶으면 여기부터** |

### 인덱스 판번호 (`schemaVersion`)

판정 단위가 바뀌면 옛 인덱스는 **다른 것을 잰 파일**이다. 이어 쓰면 조용히 섞인다.
그래서 `parse/singo.ts` 의 `PEAK_SCHEMA` 를 올리면 인덱스가 자동으로 처음부터 다시 채워진다.
(2026-08-12: 평형대 → 전용 59·84 로 좁히며 판번호 1 → 2)

### 원본 거래를 저장하지 않는 이유

2006년부터의 전 거래를 그대로 담으면 저장소가 수 GB 가 된다(현재 7개월치가 46MB).
판정에 필요한 건 "지금까지의 최고가" 한 줄뿐이라 그것만 남긴다.
특정 단지의 시계열이 필요하면 그때 `molit-collect` 로 그 구·월만 받는다.

## 7. 콘텐츠 재료 — 매일 만든다 (2026-08-12 오너 결정)

> 처음엔 **주간**("금주의 신고가", 금요일 08:00)으로 잡았다.
> 그런데 10억 돌파가 **주 1~2건**이라 카드가 빈다고 알리자 오너가
> **"주간 하지말고 매일 보내줘"** 로 바꿨다. 주간 워크플로는 걷어내고 일간에 붙였다.
> (며칠을 묶어 보고 싶으면 `node scripts/singo-digest.mjs --days 7` — 배관은 그대로다)

| | |
|---|---|
| 주기 | **매일 아침 7시** — 일간 알림과 같은 실행 안에서 |
| 기준 | 알림과 **같다** — 명부 1,000세대 ∩ 전용 59·84 ∩ 10억 단위 돌파 |
| 컨셉 A | **돌파 단지** — 10억·20억…100억 선을 넘은 단지를 한 장에 |
| 컨셉 B | **개별 카드 후보** — 오너가 몇 개 골라 각각 1장 |

### 기간을 '계약일'로 자르지 않는다

실거래 신고기한이 계약 후 30일이다. 계약일로 자르면 어제 계약분이 아직 안 들어와
**목록이 텅 빈다.** `foundOn`(우리가 확인한 날)으로 자른다 — 그날 새로 드러난 소식이
그날의 콘텐츠다. 계약일은 카드에 그대로 싣는다.

### 재료 묶기는 다시 판정하지 않는다

돌파는 **수집기가 판정 시점의 인덱스(=직전 최고가)로 이미 정확히 계산해 뒀다.**
묶는 쪽에서 다시 재면 인덱스가 그새 갱신돼 있어 틀린다. 그래서 수집기가 남긴 `milestone` 을
그대로 모으기만 한다 — 그래서 수집기가 매일 `data/datasets/singo-log/{YYYY-MM}.json` 에
히트를 쌓는다(`foundOn` = 확인한 날).

### ⚠️ 돌파 0건인 날이 정상이다

10억 돌파는 실측상 **월 8~12건**(2026-07, 명부 ∩ 전용59·84 기준)이다. 오너가 기준을
안 넓히기로 했으므로(넓히는 선택지 — 전 평형 주 4.5건 / 5억 단위 주 3.6건 /
명부 해제 주 13.2건 — 전부 거절), 돌파가 없는 날엔 **컨셉 B 후보에서 골라 개별 카드로 간다.**
산출물이 그 사실을 문구에 그대로 적는다.

| 파일 | 무엇 |
|---|---|

## 9. ⚠️ 실제로 기준이 조용히 좁아진 적이 있다 (2026-08-19 ~ 08-24)

**대기열이 일회용이 아니었다.** 예약 런이 `data/singo-queue.txt` 의 **마지막 줄**을 읽는
구조였는데, 08-19 배관 점검 때 진단용으로 민 `months=1` 한 줄이 그대로 남아
**5일간 매일 아침 알림이 1개월치만** 보고 있었다.

계약월이 전월(7월)인 신고가 건수 — 8/19을 기점으로 딱 0이 됐다:

| 확인일 | 당월(8월) 계약 | 전월(7월) 계약 |
|---|---:|---:|
| 08-13 | 27 | **7** |
| 08-14 | 4 | **3** |
| 08-16 | 0 | **5** |
| 08-17 | 1 | 0 |
| 08-19 · 21 · 22 · 23 | 78 | **0** |

**두 가지가 동시에 상했다.**
① 8월 후반에 드러나는 7월 계약 신고가를 **못 봤다**(소재 손실).
② 그 거래들이 **인덱스에도 안 들어갔다** — 7월의 높은 거래를 모르는 채로 더 낮은 8월 거래를
   신고가라 부를 수 있다. **오보 0 이 걸린 문제다.**

**그런데 그동안 배관은 초록불이었다.** 늦지도, 실패하지도, 빈손도 아니었다.
`pipeline-status` 는 "언제 돌았나"만 보고 있었고 **"무엇을 재고 돌았나"는 안 봤다.**

**고친 것 (2026-08-24 오너 결정)**

1. **예약 런과 자동 재시도는 대기열을 읽지 않는다.** 사람이 민 런(`push`)과 손으로 누른 런
   (`workflow_dispatch`)에서만 읽는다. 매일의 기준은 이 문서와 워크플로 기본값이 정본이다.
2. `pipeline-status.mjs` 에 **기준 드리프트 검사**를 넣었다 — 마지막 자동 런이 2개월이
   아니면 표 아래에 말해 준다. (넣고 나서 일부러 어긋내 잡히는지, 그리고 정상일 때·사람이 민
   런일 때 **안 잡히는지**까지 확인했다.)
3. 대기열 파일 머리에 "여기 무엇을 적든 내일 아침은 안 바뀐다"고 적었다.

**교훈**: 도는 것과 제대로 재는 것은 다르다. **초록불은 "죽지 않았다"이지 "기준대로 했다"가 아니다.**

## 10. 「계약일이 한참 전인데 왜 오늘 뜨나」 — 가장 자주 오는 질문 (2026-08-24)

오너가 이걸 **두 번** 물었다. 답이 문구에 없었기 때문이다. 이제는 알림이 스스로 말한다.

### 거르는 것은 날짜가 아니라 **인덱스**다

```
매일  계약월 2개월치 원자료를 통째로 받는다
   → 단지+타입별 최고가 인덱스와 하나씩 대조
   → 인덱스를 넘어선 것만 알림에 싣는다
   → 그리고 인덱스를 갱신한다        ← 여기가 핵심
```

오늘 뜬 거래는 **내일부터 자기 자신이 문턱**이다. 그래서 같은 건이 두 번 뜰 수 없고,
2개월치를 매일 다시 훑어도 결과는 **완벽한 하루치**가 된다.

### 계약일이 흩어지는 이유 — 신고기한 30일

계약은 3주 전에 했어도 **오늘 신고되면 국토부 데이터에 오늘 처음 나타난다.**
우리는 나타난 날 잡는다. 즉 "07.10 계약"은 7월 10일 소식이 아니라 **오늘 알려진 소식**이다.

2026-08 히트 93건 실측:

| | |
|---|---|
| 계약 → 우리가 확인, 중앙값 | **10일** |
| 계약 **다음 날** 들어온 건 | **0건** |
| 가장 오래 걸린 건 | 광명한진타운 25평 — 계약 07-10 → 확인 **08-16 (37일)** |
| `months=2` 창 밖으로 샌 건 | **0/93** ← 2개월이 맞는 창이라는 증거 |

### ⛔ 그래서 「계약일 기준 하루」는 만들 수 없다

그렇게 자르면 **알림이 매일 0건**이 된다(위 표의 첫 줄). 기준 변경이 아니라 알림을 끄는 것이다.
**요청을 실행하기 전에 그 요청이 무엇을 만들지 먼저 잰다.**

### 그래서 문구를 고쳤다 (기준이 아니라 문구다)

- 제목: `🔥 오늘 **새로 확인된** 신고가 N건 (…)`
- 목록 끝: `※ 계약일 기준이 아니라 「오늘 새로 드러난」 건입니다. / 신고까지 최대 30일 걸려 지난달 계약이 섞입니다.`

두 줄 다 **셀프테스트가 붙잡고 있다**(지우면 빨간불 — 실제로 지워 2건 실패하는 것을 확인했다).

⚠️ **알림 본문에 마크다운을 쓰지 않는다.** `notify-telegram` 은 `parse_mode` 를 안 넘겨
평문으로 보낸다 — `**굵게**` 를 적으면 별표가 그대로 찍힌다.

|---|---:|

인덱스를 다시 채우지 않으므로 되살아난 182개도 **다음에 문턱을 넘을 때부터** 뜬다.

### 무슨 일이 있었나

08-26 아침 알림이 안 왔다. 다섯 번 두드렸고 **다섯 번 다 `fetch failed`** 였다 —
HTTP 응답이 **한 번도** 없었다(상태코드 자체가 없다).

| 시각(KST) | 방아쇠 | 결과 |
|---|---|---|
| 07:14 | 예약 | 18회 시도 전부 `fetch failed` |
| 07:25 | 자동 재시도 | 같음 |
| 07:57 · 08:09 · 09:06 | 세션이 손으로 | 같음 |

키는 정상이었다(지문 `4e34245e` · 64자). 같은 호스트의 **건축물대장 서비스는 04:18 에
실제 데이터를 받아왔다**(공급면적 수집). 즉 포털 전체가 아니라 **실거래(RTMSDataSvc)
경로**가 두 시간 넘게 닫혀 있었다.

### 왜 「한 번 더」로는 모자랐나

08-24 의 교훈은 *"새 러너면 열린다"* 였다. 그래서 재시도를 **딱 1회**로 두었다.
그런데 그날 실제 회복까지 걸린 시간은 **1시간 17분**이었다. 11분 뒤 한 번 더 두드리는 것은
**같은 주사위를 너무 빨리 다시 굴리는 것**이다.

→ **+20분 · +1시간 · +2시간** 세 칸으로 간다(오너 2026-08-26). 열리는 칸에서 멈춘다.

⚠️ 「바로 한 번」 칸은 **일부러 뺐다.** 08-26 에 11분 뒤 재시도가 원 런과 똑같이 무너졌다 —
아침에 문이 닫히면 몇 분으로는 안 열린다. 되살리려면 그 실측부터 다시 본다.

### 조용한 칸

⚠️ 중간 칸의 실패는 **톡을 안 보낸다**(`quiet: true`). 안 그러면 아침에 ⛔ 가 다섯 통 쌓인다 —
08-26 에 실제로 그랬다. 말하는 것은 **첫 실패(예약)와 마지막 칸** 둘뿐이다.

⚠️ 조용한 것은 **실패한 재시도**뿐이다. **성공하면 무조건 보낸다.**
⚠️ 조용히 넘어간 칸도 `data/singo-last.md` 에는 그대로 남는다 —
**말을 안 하는 것과 기록을 안 남기는 것은 다르다.**

### 같이 고친 것

- 🔴 **연결 실패는 재시도를 한 번도 안 하고 있었다.** `molit.ts` 의 `fetchPage` 는 3회
  백오프를 도는데, `getRaw` 가 **던지면**(=`fetch failed`) 루프를 그대로 빠져나갔다.
  **HTTP 500 은 3번, 연결 실패는 1번** — 정확히 거꾸로였다. 이제 둘 다 3번 두드린다
  (401·403 은 그대로 즉시 포기 — 키 문제는 두드려도 안 열린다).
- **손으로 돌린 실패 톡에 꼬리말이 없었다.** 오너 입장에선 ⛔ 만 뜨고 누가 왜 돌렸는지
  알 수 없다. 이제 「자동 예약이 아니라 손으로 돌린 실행입니다」가 붙는다.
- **주차대수 워크플로의 거짓 초록불.** 08-26 07:44 실행이 "성공"인데 25줄 전부
  `⏭ 이미 있음` — **네트워크를 한 번도 안 탔다.** 하마터면 "주차대수는 성공했으니
  포털은 살아 있다"로 읽을 뻔했다. 이제 실제로 받아 본 건수를 세어 적고, 0이면
  「이 초록불은 API 가 살아 있다는 증거가 아닙니다」를 남긴다.

### 오늘 못 받은 건 내일 잡힌다

알림은 **최근 2개월 신고분**을 본다. 하루를 통째로 놓쳐도 그 거래들은 다음 날 실행에서
「오늘 새로 드러난」 건으로 잡힌다. **놓친 날의 신고가가 영영 사라지지는 않는다.**
